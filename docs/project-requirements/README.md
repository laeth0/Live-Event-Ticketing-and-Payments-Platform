# Concourse — Live Event Ticketing & Payments Platform

**A concurrency-engineering project specification.**

This folder is the complete requirement document for a production-shaped backend project whose
purpose is to make you *apply* everything in `../roadmap/` (lessons 00–11): transaction
boundaries, ACID, MVCC, the five anomalies, the three isolation levels, locking, deadlocks,
serialization failures, retries, idempotency, and the transactional outbox.

It is deliberately **not** a tutorial. Every feature exists because it creates a concurrency
problem that a careless implementation gets wrong, and there is a measurable test that proves
whether you got it right.

## 3. Conventions used throughout

**Identifiers.** `snake_case` in SQL, `PascalCase` in C#. Schemas are named after bounded
contexts: `catalog`, `sales`, `money`, `ops`.

**Money.** Always `bigint` in **minor units** (cents) plus a `char(3)` ISO-4217 `currency`
column. Never `float`/`double`. Rationale and the `numeric` alternative are in §12.

**Identifiers of rows.** Business entities use `uuid` primary keys generated by the
application as **UUIDv7** (time-ordered, so B-tree inserts stay at the right edge). Append-only
high-volume tables (`journal_entry`, `outbox`) use `bigint GENERATED ALWAYS AS IDENTITY`.

**Time.** Every timestamp is `timestamptz`. Ranges are `tstzrange`. The database is UTC; the
venue's local timezone is stored as data, never as a server setting.

**Isolation level.** Every write path in §7 states its level explicitly. There is no "the
default is fine" — if a handler runs at `READ COMMITTED` it is because someone wrote down why.

**SQL parameters.** Positional (`$1`, `$2`) in raw Npgsql, matching the course style. Never
string interpolation.

**Retryable errors.** Only `40001` (serialization_failure), `40P01` (deadlock_detected) and
`40000` (transaction_rollback). Everything else bubbles out. This rule is enforced in exactly
one place (`TransactionRetry`).

| Prefix | Meaning |
|---|---|
| `INV-n` | A system invariant that must never be observably violated |
| `F-n` | Functional requirement / feature |
| `TX-n` | Transaction scenario (§5) |
| `CH-n` | Required concurrency challenge (§6) |
| `T-n` | Test (§9) |

## 4. The one-paragraph description of the project

Concourse sells tickets to live events. Organizers publish events with a fixed allocation of
general-admission tickets and individually numbered reserved seats. Customers put seats on a
**time-boxed hold**, apply a **budget-capped promo code**, and check out against a
**double-entry ledger** paying from a **wallet** or a simulated card processor. Holds expire
and are reclaimed by a **reaper**; issued tickets emit events through a **transactional
outbox**; support agents issue **partial refunds**; organizers **withdraw settled funds**
subject to a rolling reserve. Every one of those sentences is a concurrency problem: the
system's entire difficulty is that thousands of people do them to the same rows at the same
moment, and no interleaving is allowed to oversell a seat, create money, or double-charge a
card.
